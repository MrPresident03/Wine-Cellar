# ADR 0001 — House of Vino architecture

Status: accepted (milestone 0), 17 Oct 2026. Later changes get their own ADR.

Decisions marked **⚑** affect privacy, recurring cost, data licensing or irreversible data changes and need the owner's sign-off before release.

## Context

A premium, offline-first wine collection manager for iOS and Android: accurate inventory for hundreds to thousands of bottles, excellent search, tasting journal, wishlist, physical locations, insights, CSV import/export, scanning. The spec fixes the stack: Kotlin Multiplatform, Compose Multiplatform, SQLDelight/SQLite, Supabase/PostgreSQL.

## Decisions

### 1. Modules

```
shared/core   pure Kotlin (no I/O): money & decimals, domain rules, ledger validation,
              text folding, search query parsing, CSV parsing/mapping, label parsing, insights maths
shared/data   SQLDelight database, repositories, search engine, sync engine,
              Supabase remote, file/photo store            -> depends on core
shared/ui     Compose Multiplatform: design system, screens, view models, navigation,
              app graph (manual DI); builds the iOS framework "HouseOfVino" -> depends on data
androidApp    Activity, Android services (CameraX + ML Kit, WorkManager, notifications)
iosApp        SwiftUI host generated by XcodeGen; iOS services via Kotlin/Native interop
supabase/     SQL migrations, row-level security, pgTAP tests, Edge Functions
```

Targets: Android, iOS (arm64 + simulator arm64), and JVM. The JVM target exists for fast tests and for rendering UI screenshots in CI; it is not shipped. Intel iOS simulators are not targeted.

Dependency injection is a hand-written `AppGraph` (constructor injection). It keeps startup and tests simple and avoids a framework dependency for a graph of about twenty objects.

### 2. Local database: SQLDelight on a bundled SQLite

SQLDelight generates type-safe queries from SQL. Its stock Android driver uses the phone's system SQLite, which varies by OS version and does not reliably include FTS5. We ship SQLite inside the app instead (`androidx.sqlite:sqlite-bundled`) on Android, iOS and the JVM, through a small SQLDelight driver (`BundledSqlDriver`). Every platform and every test therefore runs the same SQLite build with FTS5 and JSON1. Cost: roughly 1–2 MB per Android ABI.

- The schema is defined by numbered migrations (`migrations/N.sqm`), with `PRAGMA user_version` as the version. Creation and each migration run in one transaction.
- One connection guarded by a re-entrant lock; WAL mode; foreign keys on.
- Dynamic search SQL is built in Kotlin with bound parameters only; all other SQL is compile-time checked by SQLDelight.

### 3. Data model

Full schema: [docs/schema.md](../schema.md). The essentials:

- **Wine identity ≠ vintage ≠ inventory.** `wine` (producer + cuvée) → `wine_vintage` (year, NV or unknown) → `lot` (an acquisition batch: size, price, source, date, case) → `stock` (bottles of a lot at a location).
- **Append-only ledger.** Every stock change is an `inventory_movement` row (purchase, consume, sell, gift, loss, transfer, count correction, reversal). Balances are derived from it and are never edited directly. Corrections are reversals that point at the original. SQLite triggers reject updates/deletes of ledger rows; the server only accepts movements through one function.
- **Nothing that matters is hard-deleted.** Synced rows are soft-deleted (`deleted_at`). Tasting notes reference the vintage, not the stock, so consuming or selling never touches them.
- **No silent merges.** Duplicate detection proposes; the user confirms. Different vintages are never merged automatically.
- **Money is exact.** Integer minor units + ISO currency. Decimal strings for rates, ABV and ratings. 128-bit intermediate arithmetic for conversions, verified against `java.math` in tests. Amounts in different currencies are kept apart unless converted with a recorded rate (source and date).
- **Estimated values carry provenance.** `market_value` rows always have source, currency and date. The app never invents prices, ratings, drinking windows or wine metadata.
- **IDs** are UUIDv7 strings created on the device.

### 4. Offline-first sync with Supabase

- Every write lands in SQLite first, inside a transaction that also enqueues a `sync_outbox` row. The UI never waits for the network.
- **Records** (wines, vintages, lots, notes…) push as upserts with optimistic concurrency: the server row's `rev` must equal the `rev` the device last saw. On mismatch the device fetches the server row and does a three-way field merge using the stored base snapshot. Non-overlapping edits merge automatically; overlapping edits keep the server version and record a `sync_conflict` for the user to resolve.
- **Stock** changes push as ledger movements through a Postgres function (`apply_inventory_movement`) that is idempotent by movement id, locks the affected balances and refuses to go below zero. Two phones opening the "last" bottle offline is resolved deterministically: the first to sync wins, the second movement is rejected and surfaced, and balances on both phones converge.
- **Pull** is incremental per table by a server-assigned revision from one global sequence; tombstones are rows with `deleted_at`.
- Retries use exponential backoff with jitter; operations are idempotent, so retrying after a lost response is safe.
- Background sync: WorkManager (Android) and BGTaskScheduler (iOS), plus sync on app foreground and after each local write when online.
- **Local-only mode:** the app works fully without an account. Signing in later uploads the local household. ⚑ Local-only data has no cloud backup; the app says so and offers export.

### 5. Security and privacy ⚑

- Row-level security on every table: a row is visible only to members of its household. Roles: owner, editor, viewer. Membership and invites are managed by security-definer functions, never by direct table writes.
- The app ships only the Supabase URL and the public anon key. No service-role key, ever. Privileged operations (account deletion) run in an Edge Function.
- Photos live in a private Storage bucket under `<household_id>/…`, with storage policies matching table RLS.
- Account deletion is in-app (required by the App Store): it removes the user's memberships, deletes households they alone own (after offering an export), deletes their photos and the auth user, then wipes the device.
- Supabase project region should be chosen near users (e.g. Sydney for NZ/AU). ⚑

### 6. Search

- SQLite FTS5 index (`search_fts`) with `unicode61 remove_diacritics 2` tokenisation and prefix indexes; documents for vintages (cellar scope), wishlist items and tasting notes. Indexed: producer, name, vintage, region/appellation/classification, grapes, tags, notes. bm25 ranking weighted toward producer and name.
- Index rows are maintained by the repositories inside the same transaction as the data change (local edits and sync alike), plus a full rebuild after migrations. A test compares the index with the source tables.
- Typo tolerance: terms with no hits are widened using the FTS5 vocabulary (words that actually exist in the user's data), with an edit-distance allowance by term length.
- Structured filters (style, country, region, grape, vintage range, size, location subtree, tags, drinking status, rating, formerly owned) are joined in SQL; results are paged; nothing loads the whole collection.
- Scopes: Cellar, Wishlist, Tasting notes, Discover (external catalogue — empty unless a provider is configured).
- Target: < 50 ms for a typical query on 5,000+ bottles on a mid-range phone; CI measures on a 20,000-vintage synthetic collection.

### 7. Integrations behind interfaces

`BarcodeScanner`, `LabelTextRecognizer`, `WineCatalog`, `PriceSource` and `FxRateSource` are interfaces in `core`.

- On-device scanning: ML Kit (Android) and Apple Vision/AVFoundation (iOS). No network, no cost.
- A barcode is never treated as a unique wine identity. A scan yields candidates from the user's own `barcode_link` history and optional catalogues; producer, vintage and size are always confirmed.
- External catalogue / price providers are off by default. ⚑ Candidates: Open Food Facts (free, ODbL — attribution and share-alike apply to the database, sends the barcode to a third party), commercial wine APIs (paid; licences restrict caching and display). None is integrated until the owner chooses.
- FX rates: user-entered by default; the European Central Bank reference rates are a free optional source. ⚑
- Every integration has a complete manual path.

### 8. UI

- Compose Multiplatform with Material 3 as the component base, restyled by the House of Vino design system ([docs/design-system.md](../design-system.md)).
- Navigation 3 (`navigation3-ui`): the back stack is app state, which suits list/detail on tablets and deep links.
- View models from `lifecycle-viewmodel-compose`; state as immutable data classes exposed as `StateFlow`.
- Every screen has designed loading, empty, error, offline, permission-denied and success states.

### 10. Build and CI

- Gradle 9.7.0 wrapper, version catalog in `gradle/libs.versions.toml`.
- GitHub Actions on the `house-of-vino` branch: Linux job (JVM + desktop tests, Android APK), macOS job (Kotlin/Native simulator tests, iOS framework, Xcode build), Supabase job (migrations, RLS tests, sync integration tests). Results are also pushed to `ci/*` branches.
- ⚑ The repository is public, so this source code is public. No secrets are committed; build secrets go in GitHub Actions secrets or local `secrets.properties`.

## Consequences

- Two persistence paths (local SQLite, remote Postgres) must stay in step: each migration exists in both places and CI checks both.
- The bundled SQLite adds APK/IPA size but removes a whole class of device-specific bugs.
- The ledger makes "fix a typo in a quantity" a reversal plus a new movement rather than an edit. The UI hides this behind "Correct count", but exports show the full trail.
